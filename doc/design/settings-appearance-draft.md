# Settings dialog — Appearance draft

Appearance design, accepted for the first Settings page. Later sections remain proposals.

[Open the SVG](settings-appearance-draft.svg). It shows one screen: Appearance, with
the five planned section names present. The neutral/green palette is the application's current
default. The title decoration is illustrative; the application will use the system's
decoration through `DialogWindow`, not implement another title bar.

The window keeps the compact desktop controls and subtle button gradients. Navigation
uses the existing rounded list selection and quiet pane-focus frame. Appearance is
selected and the section list has keyboard focus in this illustration; the example list
inside the preview is inactive. There are no shadows or raised cards.

## Layout and behaviour

- Left: Appearance first; Viewing, Browser, Files and Thumbnails will follow page by page.
  The implementation shows only available pages. Info panel configuration is omitted:
  its existing window/fullscreen and preview/view behaviour already fits its purpose.
- Appearance: three labelled sliders paired with numeric inputs, followed by a controls
  preview. The whole application's chrome should preview the palette as well.
- Initial values: hue 150°, accent chroma 0.075, surface chroma 0.000. Zero surface tint
  keeps surfaces and ordinary text neutral. Apply is disabled because nothing changed.
- **Apply** persists validated changes and establishes a new cancellation checkpoint.
  **OK** does the same and closes. **Cancel**, window close and Escape discard changes
  since the last Apply and restore that palette. An open popup/editor handles Escape first.
- Switching sections retains the draft. Only Appearance needs live preview in this first
  design; other preferences can take effect on Apply.
- **Reset appearance** resets these three draft values to their defaults. It does not
  reset other sections or persist anything until Apply/OK.
- Footer button ordering should follow platform conventions in implementation; the SVG
  shows one proposed arrangement. Enter must first commit the active numeric editor.

The preview uses a list, check box, text field and buttons as visual samples. They do not
represent additional preferences or perform file operations. Existing `Slider`, `SpinBox`,
`DecimalSpinBox`, `CheckBox`, `Button`, `ListFrame` and list-delegate treatments suffice;
no new user-facing control type is proposed.

For this draft, Hue spans 0–360°, Accent strength 0–0.15, and Surface tint 0–0.04. The
chroma steps are 0.001. These UI ranges emphasize useful subtle changes; if an existing
saved value exceeds them, the control expands to show it without silently clipping.
The backend accepts chroma up to 0.4. Numeric fields display raw chroma for now.

## Implementation boundary

Editable controls do not write directly to persistent `Preferences` during preview.
`AppearanceDraft` holds their values. A process-wide `ThemePalette` supplies a temporary
runtime palette override; Apply copies validated values to Preferences, and Cancel
removes the override and restores the latest saved values. A second Settings window
activates the existing editing session, so two previews cannot compete. Settings opens
from Tools and remembers its window size through `DialogWindow`.

Thumbnail cache entries already include the requested edge size in their key (along
with path and colour target), so future thumbnail size changes can reuse independent
sizes without clearing the cache. No thumbnail controls are added in this first page.

Viewing must later distinguish requested from actual output depth and explain restart
requirements. Clear-cache and clear-history actions need explicit immediate-action
wording because cancellation cannot restore them. Those sections are not drawn in this
first screen.
